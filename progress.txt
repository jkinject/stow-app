[근본 원인] thumbs.ts 헤더에 "expo-image 의 디스크 캐시가 실제 바이트를 잡아준다" 고
  적혀 있었는데 **사실이 아니었다.** expo-image 는 URL 전체를 캐시 키로 쓰는데,
  Supabase 서명 URL 은 서명할 때마다 token(JWT)이 달라진다. 실측 확인:
  같은 파일을 1.5초 간격으로 두 번 서명 → 물음표 앞은 동일, 전체 URL 은 상이.
  즉 캐시가 **한 번도 맞은 적이 없고** 매번 통째로 다시 내려받고 있었다.

[고친 것]
1. `cacheKey` = **저장 경로**. 경로는 사진 교체 시 새 버전 uuid 가 붙으므로
   내용이 바뀌면 키도 바뀐다 — 캐시 키로 정확히 맞는 값.
   근거(native): expo-image/android .../okhttp/ExpoImageOkHttpClientGlideModule.kt
   "Glide store its bytes under [cacheKey], so a later load using the same cache key hits the cache."
   → get() 이 문자열이 아니라 `{ uri, cacheKey }` 를 통째로 돌려준다. 쓰는 쪽에서
     빠뜨릴 수 없게 하려는 것. 빠뜨리면 조용히 예전 상태로 되돌아간다.
   덤: 토큰이 만료돼도 이미 받아둔 사진은 그대로 뜬다.
2. 서명 캐시를 **모듈 단위**로. 전에는 화면마다 useState 라 탭을 옮길 때마다 비워졌고,
   돌아오면 보이는 것 전부를 다시 서명 = 다시 다운로드였다.
3. `cachePolicy="memory-disk"`. expo-image 기본값은 'disk' 라 메모리 캐시가 없어서
   스크롤을 조금만 왕복해도 디스크에서 다시 읽고 다시 디코드했다.
4. `recyclingKey` — 격자 셀 재활용 시 이전 사진이 잠깐 비치는 것 차단.

[하마터면 다시 낼 뻔한 버그] 저장소를 모듈로 빼면서 useCallback 을 [] 로 두었더니
  `thumbs` 참조가 영원히 고정됐다. 찾기 탭은 renderItem 을 useCallback([.., thumbs])
  로 memo 한 FlatList 라 **서명이 끝나도 셀을 다시 그리지 않는다.** 이 파일에 이미
  같은 종류(URL 을 ref 에 담았던 건)가 있었다. 해결: 스냅샷 Map 을 제자리에서 고치지
  말고 **갈아끼우고**, get() 이 구독한 스냅샷을 읽게 한다. 그러면 참조가 자연히 갈린다.
  (lint 가 "불필요한 의존성 v" 라고 경고한 게 단서였다 — 억누르지 말고 구조를 고칠 것)

  ②가 실패하면 `photo_failed` 상태를 적었는데 —

    · 상태를 들고 있던 화면은 ①에서 이미 언마운트됐다
  그래서 실패가 흔적 없이 사라졌다. 재시도할 방법도, 실패했다는 사실을 알 방법도 없었다.
